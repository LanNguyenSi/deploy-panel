## Relay success is a claim, not a verdict

No deploy is written to the database as `status: "success"` on the relay's word alone. `finalizeDeploy` (`backend/src/lib/stream-deploy.ts:42-94`) is the choke point every relay-reported outcome that could plausibly be a success funnels through, and it re-verifies before trusting a reported success.

`streamDeploy` (stream-deploy.ts:100-310) hands `finalizeDeploy` exactly three shapes of relay outcome that could be a success, all converging on the same function:

1. **SSE `done` event** (`handleEvent`, stream-deploy.ts:350-362) — the relay finished streaming and reported `success`/`failure` explicitly.
2. **JSON fallback** (stream-deploy.ts:196-235) — the relay doesn't support streaming and returned a single JSON body instead; `success` is derived from `data.result.success` or `data.deploy.status`.
3. **Stream ended without a `done` event** (stream-deploy.ts:273-286) — the connection closed cleanly but no terminal event arrived; success is inferred from whether every accumulated step reports `"success"` or `"skipped"`.

A fourth shape bypasses `finalizeDeploy` entirely: a **relay 4xx rejection** (stream-deploy.ts:181-190): the relay definitively rejected the deploy request (unknown app, bad branch), not a connection that dropped mid-flight. This is written straight to `status: "failed"` without going through `finalizeDeploy`, because it can never be a `relaySuccess: true` claim needing verification; there is nothing to downgrade. Routing it through the catch block's `recoverBrokenDeploy` instead would run the post-deploy health probe against whatever the PREVIOUS successful deploy left running, greenwashing a real rejection into a "success" row (the bug PR #124 fixed for rollback; the same reasoning is why both rollback routes' own RelayError-4xx branches, routes/apps.ts and routes/v1.ts, also write `failed` directly instead of calling `recoverBrokenDeploy`). 5xx and a missing body still fall through to the generic throw, which the catch block routes through `recoverBrokenDeploy` as before, since those can't be told apart from a dropped connection.

Whenever any of the three finalizeDeploy-routed shapes report `relaySuccess: true`, `finalizeDeploy` runs `verifyDeployHealth` (`backend/src/lib/post-deploy-gate.ts`, `verifyDeployHealth` near the end of the file) — container run-state via `docker compose ps` plus a public-route probe — and DOWNGRADES `success` to `false` if the verdict is unhealthy (stream-deploy.ts:53-74). A relay-reported failure routed through `finalizeDeploy` is written straight through with no second-guessing (the doc comment at stream-deploy.ts:32-40 states this explicitly). The gate exists because the relay's own internal health probe stops at the first container that answers, so a crashlooping sibling service, or a broken Traefik route invisible from inside the container network, can hide behind a `docker compose up` exit code of 0 (post-deploy-gate.ts:9-21).

## Fail-closed vs. fail-open: two calling conventions for the same gate

`verifyDeployHealth` takes a `requireHealthyEvidence` flag (doc comment on `VerifyDeployHealthOptions` in post-deploy-gate.ts) that inverts its default posture:

- **Default / optimistic (`false`)**, used by `finalizeDeploy` on the relay-success path: the absence of a bad signal is enough — an unreachable relay or an empty `docker compose ps` does not, by itself, fail the gate, because a real success signal already exists. Since 2026-08-17 this is qualified for Docker healthchecks that have not RESOLVED yet: a service with `health: "starting"` is neither offender nor clean evidence — the gate keeps polling within a bounded extension (`pendingExtraAttempts`, default 9 extra polls, so the optimistic window can grow from the base 4 × 5s ≈ 15s up to ~60s), an unreadable poll while something was "starting" carries the watch forward instead of passing, and if the window exhausts still-"starting" the deploy passes optimistically WITH a `notes` entry naming the unresolved service(s) and any offender seen earlier in the window.
- **Strict / fail-closed (`true`)**, used by connection-lost recovery below (startup recovery shares the posture via a lighter relay preflight, not this gate): there is NO success signal to trust, so only a POSITIVE confirmation (≥1 running service, none unhealthy, none still `"starting"`, and the route if set) counts; an unreachable relay, nothing running, or an unresolved healthcheck keeps the deploy `failed`. Consequence: a healthy-but-slow healthcheck (long `start_period`, Docker's default 30s interval) can consume the recovery window and be recorded failed — the reason string names the still-starting services. Margin reality check: deploy-panel's OWN images declare `HEALTHCHECK --interval=5s --timeout=3s --start-period=15s --retries=4` (backend/Dockerfile, frontend/Dockerfile; the prod compose overrides only db), so a healthy container resolves within ~5s of a recreate and a broken one is reported unhealthy by ~31s when the probe fails fast (15s start period + 4 x 5s) and by up to ~50s when the probe hangs (Docker starts the next probe one interval after the previous one completes: 15s + 4 x (5s + 3s) + 3s), inside the ~60s optimistic window; in strict recovery an unhealthy and a still-starting container both end `failed`, so the margin matters only for the healthy case. agent-tasks' frontend (5s interval, 10s start_period) resolves comparably. A service with the Docker default 30s interval would stay "starting" for ~30s and make every optimistic finalize take the pending extension, which is why the panel's own images no longer use it.

**Connection-lost recovery** (`backend/src/lib/deploy-recovery.ts`, `recoverBrokenDeploy`) is invoked from `streamDeploy`'s catch block (stream-deploy.ts:287-306) whenever the relay fetch/stream throws, awaited with its own `.catch` (not fire-and-forget), so a rejection from `recoverBrokenDeploy` itself is logged and swallowed instead of becoming an unhandled rejection. It runs `verifyDeployHealth` with `requireHealthyEvidence: true` over 5 polls × 12s (deploy-recovery.ts:135-140#"const RECOVERY_INTERVAL_MS = 12_000;", passed as `requireHealthyEvidence: true` at deploy-recovery.ts:267-274#"requireHealthyEvidence: true") — containers are typically mid-recreate when a stream drops, so it deliberately waits before deciding. The same function is now also called directly (not via `streamDeploy`) from both rollback routes' non-4xx error paths, and self-registers via its own `registerActiveDeploy`/`releaseActiveDeploy` try/finally (deploy-recovery.ts:226-230#"releaseActiveDeploy(deployId);", inside `recoverBrokenDeploy` at deploy-recovery.ts:207-230#"releaseActiveDeploy(deployId);") so the stuck-sweep exclusion above applies to those callers too. (Note: since the pending-health change the OPTIMISTIC gate's worst-case window, ~60s with the pending extension, is about the same length — the recovery path is stricter in posture, no longer simply "longer".)

A healthy verdict is still not enough for a **deploy** (`kind: "deploy"`, the default): a relay cut off before the git pull leaves the OLD containers running and healthy, so the probe is true for a deploy that never ran. After a healthy verdict with no rollback or failed step in the log, `recoverBrokenDeploy` runs `checkDeployTarget` (`backend/src/lib/deploy-target.ts:283-323#"return { reached: false, failedCheck };"`), the same check the stuck sweep uses (see the next section): no later panel Deploy row for the app, and a relay `success` entry for this deploy (matched by its id whenever the relay is id-capable, by the timing correlation only for a relay that is not) whose `commitAfter` is the repo HEAD. Without that proof the row is written `interrupted`, the `recovery` step names the failed check (`check failed: target not reached: ...`), and the app card is set `healthy` (the old version really is up) without moving `lastDeployAt` (deploy-recovery.ts:316-317#"marking deploy interrupted", app update at deploy-recovery.ts:333-334#"lastDeployAt stays as it was."). A start time that cannot be read from the row is a failed check, never a pass. Unlike the sweep, the panel's own app gets no preflight-only exemption here: the exemption rests on the sweeping process being the recreated panel, whereas this function only reaches the check while the process is alive, i.e. while this deploy has not yet replaced the panel's containers. Residual: when the relay is still finishing the deploy at check time it has not recorded the entry yet, so a deploy that completes later is recorded `interrupted` (fail closed). The two rollback routes also send their Deploy row id and pass `kind: "rollback"`, which runs the same check through the id match only (`checkDeployTarget`'s `idPathOnly`): the rollback's relay entry carries no duration, so the timing correlation cannot apply to it. Against an id-capable relay the rollback's own id-matched entry must be a `success` whose `commitAfter` is the repo HEAD, otherwise the row ends `interrupted`; against a relay that is not id-capable (see the capability rule in the next section) the recovered rollback keeps the health-only verdict, so a rollback that never ran while the old version stays healthy still ends `success` there. For `idPathOnly` the relay is asked first, so a non-id-capable relay is never failed on a later panel row.

**Startup stuck-deploy recovery** (`backend/src/lib/startup.ts`, `recoverStuckDeploys`) handles deploys still `status: "running"` more than 2 minutes after creation — the shape left behind by a self-deploy that killed the backend process mid-response, or a deploy orphaned by any other process restart. It uses a lighter relay `preflight` check rather than the full gate, but the same fail-closed posture: relay-unreachable or preflight-not-passed both resolve to `"interrupted"`, never `"success"` (startup.ts:133-162#"Relay unreachable or app not found"). A passing preflight alone is not enough for any app except the panel itself: it only says containers are running, which is also true for a deploy cut off before the git pull (the old containers still run). Two further checks must pass before `"success"`:

- **No later panel deploy row.** If any other `Deploy` row for the same app has a `createdAt` after this record's (a panel deploy, rollback or scheduled deploy), the record is `"interrupted"` with a step naming that row, and the relay is not asked for history: the later action may be what moved HEAD (deploy-target.ts:305-307#"select: { id: true }"). Both this guard and the history check below live in `checkDeployTarget`, shared with `recoverBrokenDeploy`.
- **The relay's history must single out this deploy.** The panel sends its Deploy row id as the `X-Deploy-Id` header on every relay deploy call (`streamDeploy`, stream-deploy.ts:159-166#"signal: AbortSignal.timeout(600_000)") and both rollback calls (`relayRequest`'s `headers` option, routes/apps.ts and routes/v1.ts), and agent-relay stores it on the history entry as `deployId`. The sweep reads `GET /api/apps/:name` and `assessTargetReached` (`backend/src/lib/deploy-target.ts:166-229#"return assessEntryOutcome(entry, head);"`, re-exported from startup.ts) requires, from the relay's `recentDeploys` (agent-relay `DeployRecord`: `status`, `commitAfter`, `createdAt`, `durationMs`, `triggeredBy`, optional `deployId`; newest first, at most 10): **id match first.** When any entry in the history carries a `deployId`, the relay is known to record ids, and the entry whose `deployId` equals this record's id IS this deploy's entry: no other deploy, rollback or non-panel call can be mistaken for it, none carrying the id means the deploy left no entry (not reached, fail closed), and the correlation (a)-(c) below is skipped, while (d) and (e) still apply to that entry. **Capability.** The relay counts as id-capable when its public `GET /health` reports a `version` at or above `RELAY_DEPLOY_ID_MIN_VERSION` (`relayVersionSupportsDeployIds`, read on every check, nothing cached, so a panel restart changes nothing) or when any history entry carries a `deployId`; an id-capable relay with no entry for this id is not reached even when the recent history holds no id-bearing entry (the first deploy after a relay upgrade), which closes the non-panel-deploy residual for such relays. **Fallback**, documented and kept: a relay whose `/health` cannot be read or reports no version, and whose history shows no `deployId` at all (an older relay), is judged by the correlation (a)-(e). The same check finalizes a stuck panel rollback row: when its own id-matched relay entry succeeded and matches HEAD the row ends `success` (previously always `interrupted`). A relay `400` for the id on the streaming deploy call is the 4xx rejection above (the row ends `failed`, never `recoverBrokenDeploy`). (a) exactly ONE entry recorded at or after this record's `createdAt` (the comparison is inclusive; none means the deploy never got that far, more than one is ambiguous because a rollback or redeploy entry also ends on HEAD whatever this deploy did; fallback residual: when this deploy left no entry, a single later non-panel deploy over the relay's HTTP API is indistinguishable; it applies only to a relay that is not id-capable, since an id-capable one is judged by the id match); (b) that entry's `triggeredBy` is `"api"` (an entry without one is rejected), the trigger the panel's own streaming deploy call records (an MCP-triggered entry is somebody else's); (c) its `durationMs` is positive (agent-relay's rollback records none, so a rollback entry is rejected) and its own start, `createdAt` minus `durationMs`, is not earlier than this record's start by more than `RELAY_CLOCK_TOLERANCE_MS` (10 s, the slack for host clock skew, since the panel stamps the row before it calls the relay); (d) its `status` is `success`; (e) the repo's current HEAD (`app.commit`, a short sha) prefix-matches that entry's `commitAfter` (`commitsMatch`, deploy-target.ts:106-110#"startsWith(y)", with a 7-character minimum so a short value cannot match everything). The target is always the relay entry's `commitAfter`: the deploy row carries no commit while it is `running` (commit columns are written at finalize), so the record is never a target source.

The relay records every non-blocked deploy result, failures as `failed`, so only a `success` entry implies build, up and health all passed; even then `compose up -d` on an unchanged image does not recreate the containers, so the check proves the deploy ran to its end on the matching commit, not that containers restarted. The two clocks (relay host and panel database) are compared in (a) and (c) and the skew can go either way. Relay behind: a real success can look `"interrupted"` (fail closed). Relay ahead: an earlier deploy can look as if it ended after the start; (c)'s start-of-entry guard covers that unless the skew is roughly the earlier deploy's duration plus the tolerance and that earlier deploy is the only entry in the window, so a grossly wrong relay clock remains an unguarded residual. A failed check leaves the record `"interrupted"` and the `startup-recovery` step names it (`check failed: target not reached: ...`). The panel's own app (relay app name `deploy-panel`, overridable via `PANEL_SELF_APP_NAME`, matched by app name only; `isPanelSelfApp`, startup.ts:35-37#"DEFAULT_PANEL_SELF_APP_NAME);") keeps the preflight-only verdict: the sweeping process is by construction the recreated panel, and the relay may still be finishing the deploy (not yet recorded it) when the sweep first looks.

`recoverStuckDeploys` now runs periodically (every `CHECK_INTERVAL`, driven by `scheduler.ts`'s `startScheduler`), not only once at process boot: a deploy that was younger than the 2-minute threshold when the process booted (still legitimately in flight at that moment) would otherwise age past it later with nothing left to ever sweep it. Running periodically means each pass can now observe deploys genuinely still streaming in THIS process; it must not treat those as stuck just because they've run a while. Three things keep that safe:

1. **Exclusion set.** The active-deploy registry (`registerActiveDeploy`/`releaseActiveDeploy`/`isActiveDeploy`/`listActiveDeployIds`, deploy-recovery.ts:8-100#"return activeDeployRefCounts.get(deployId) ?? 0;" for the module comment, the refcounted `Map`, and the functions themselves), consulted via `listActiveDeployIds()` as the stuck-sweep query's `id: { notIn }` filter (startup.ts:98-99#"const idFilter = activeIds.length > 0"), holds every deploy id a process is actively driving: `streamDeploy` registers/deregisters its id for the run's duration, both rollback routes (`routes/apps.ts`, `routes/v1.ts`) do the same around their own `relayRequest` call, and `recoverBrokenDeploy` (deploy-recovery.ts:207-230#"releaseActiveDeploy(deployId);") registers/releases itself too so any caller gets the exclusion for as long as its own health-check polling runs. Registration is refcounted rather than a plain Set: `recoverBrokenDeploy` always self-registers on top of whatever the caller already registered, so a caller releasing its own hold must not delete `recoverBrokenDeploy`'s still-pending one for the same id — the ordering invariant this depends on is documented in the module comment (deploy-recovery.ts:18-38#"carried over from the old flag."). A running record NOT in this set is either orphaned by a past restart or was started by a process that has since died.
2. **Compare-and-set finalize.** Each candidate is finalized with `prisma.deploy.updateMany` scoped to `status: "running"` (startup.ts:189-193#"log: JSON.stringify([...existingSteps, recoveryStep]),"), not a plain `update`: if another path already resolved that exact record between the query and this write, the `count` comes back `0` and the pass leaves it (and the app status) alone instead of overwriting a newer verdict. The app-status write is additionally skipped when a still-active sibling deploy exists for the same app (startup.ts:208-213#"if (!liveSibling) {"), so reclaiming an old orphaned record for an app can't clobber a genuinely live deploy's "deploying" status.
3. **Re-entrancy guard.** A module-level `sweepInFlight` flag (startup.ts:22#"let sweepInFlight = false;", checked in `recoverStuckDeploys` at startup.ts:80-86#"sweepInFlight = false;") makes a second call a no-op while a pass is still running: each stuck deploy costs a `relayRequest` with up to a 300s budget, so a pass can outlast the 60s interval.

## Rollback outcomes and the app status

Both rollback routes (`routes/apps.ts`, `routes/v1.ts`) drive their deploy record directly, so they also own the app card's status for the outcomes they finalize themselves, through the shared helper `setAppStatusAfterRollback` (`lib/rollback-app-status.ts`). A relay result that is blocked by preflight or reports `success: false` sets `App.status` to `unhealthy`. A relay-reported rollback success is not taken at face value for the app card: it goes through `verifyDeployHealth`, the same gate `finalizeDeploy` uses, and only a passing verdict writes `healthy` plus `lastDeployAt`, a failing one writes `unhealthy`. The rollback row itself is still written `rolled_back` from the relay's word before the gate runs (only the app card is gated). The v1 route is already async after its `202`; the apps route has responded by the time the gate runs, so its response does not wait for it. The write comes after the deploy row's terminal update and the helper never throws (a failed write or gate error is logged and leaves the app status as it was), so a failing app update cannot fall into the route's catch block and hand an already-finalized row to `recoverBrokenDeploy`. The relay-4xx branch writes the row `failed` directly and then branches on the `phase` agent-relay attaches to its rollback error body (`before_reset` or `after_reset`, additive; `relayRequest` stores the response text on `RelayError.body` and also folds it into the message; `rollbackFailurePhase` in `lib/rollback-app-status.ts` parses the body first and falls back to the message, for an error built without a body): `setAppStatusAfterRollbackRejection` sets `App.status` to `unhealthy` only for `after_reset` (the relay attempted `git reset --hard`, so the tree may have moved or be partly rewritten and the app may be broken) and leaves it untouched for `before_reset` (bad ref, unknown app; HEAD did not move). A missing or unknown phase, which is what an older relay sends, is treated as `before_reset`, so deploy-panel can ship before the relay is redeployed. A 5xx or transport `RelayError` stays routed through `recoverBrokenDeploy`: the relay-side error cannot tell a rollback that never ran from one that ran and then dropped the connection, so the health gate decides both the deploy row and the app status, and the route itself writes neither; a rollback that never ran while the old version stays healthy still ends as `success`. `POST /api/v1/rollback` answers `202` with `status: "running"` and is async: the terminal state (`rolled_back`, `failed`, or `success` when the 5xx recovery path finalized it) is only readable by polling `GET /api/v1/deploy/:id`.

## This is the mechanism behind the self-deploy-502-but-succeeds quirk

Deploying deploy-panel's own backend kills the backend process mid-HTTP-response, so the browser/CI client sees a 502 (or a dropped connection) even though the deploy itself proceeds correctly on the relay side. The 502 is a client-side artifact of the connection dying, not a deploy failure: `streamDeploy`'s catch block fires `recoverBrokenDeploy`, which fail-closed re-verifies health and confirms the deploy as `success` only if the app is genuinely healthy and the relay's history proves this deploy reached its target (a panel process killed mid-deploy never gets that far; its record is then picked up by the sweep below). If the backend restarts before `recoverBrokenDeploy` finishes for an in-flight deploy, `recoverStuckDeploys` catches it on its next periodic pass (every `CHECK_INTERVAL`, not only at the next process boot: see the "Startup stuck-deploy recovery" section above) and does the equivalent check via `preflight` (the panel's own app keeps that preflight-only verdict; see the "Startup stuck-deploy recovery" section for why other apps additionally need relay proof of the target). Either path can turn a 502-shaped client experience into a correctly-recorded `success` — this is expected behavior, not a bug: verify via `GET /api/deploys` or the DB rather than trusting the client-observed HTTP status of a self-deploy request.

## Scheduled deploys share the exact same path

`checkScheduled` (`backend/src/lib/scheduler.ts:38-103`) calls `streamDeploy` directly (scheduler.ts:93-101) rather than hitting the relay via a second, divergent call. The comment at scheduler.ts:83-92 documents why: an earlier version called the relay directly from the scheduler and skipped BOTH the pre-deploy secret provisioning and the required-env hard-fail gate, reproducing the exact `METRICS_API_TOKEN`-missing incident for scheduled deploys specifically. Routing scheduled deploys through `streamDeploy` means they get the same secret provisioning, the same three-shape relay handling, and the same trust chain described above — one implementation, not two.

## What breaks it

- Writing `deploy.status = "success"` anywhere outside `finalizeDeploy` on a relay-reported success — that bypasses `verifyDeployHealth` entirely and reopens the exact crashloop-as-healthy hole the gate exists to close.
- Adding a relay-response shape that CAN report success (e.g. a new streaming protocol) and doesn't funnel through `finalizeDeploy` — it would silently skip the health gate for that shape alone. (The 4xx-rejection shape at stream-deploy.ts:181-190 is a deliberate exception to "funnels through finalizeDeploy": it can only ever be a failure, so there is no success claim to verify.)
- Finalizing a `"running"` deploy record from the stuck-sweep with a plain `update` instead of the compare-and-set `updateMany` (startup.ts:189-193#"log: JSON.stringify([...existingSteps, recoveryStep]),"): that reopens the false-finalization race the compare-and-set exists to close, since a record another path (a rollback route, `recoverBrokenDeploy`) already resolved between the sweep's query and its write would get silently overwritten.
- Letting `recoverBrokenDeploy` write `"success"` for a deploy on a healthy probe alone, or defaulting its `kind` to `"rollback"`: the old containers answer healthy when the relay stopped before the git pull, so the row would read as a success for a deploy that never ran.
- Letting the stuck-sweep write `"success"` for a non-panel app on a passing preflight alone (or dropping the later-deploy-row check or the exactly-one-entry, trigger, duration and start-of-entry guards in `checkDeployTarget` / `assessTargetReached`): a deploy cut off before the git pull then reads as a success while the old commit still runs (the event-booking-system incident); a rollback or redeploy recorded after the stuck start would equally read as its success. Equally, widening the preflight-only exemption beyond the panel's own app reopens it.
- Driving a deploy record's terminal status directly (not via `streamDeploy`, and not via `recoverBrokenDeploy`) without first calling `registerActiveDeploy` on its id: the periodic stuck-sweep has no other way to know the record is still genuinely in flight, and can finalize it out from under the caller once it crosses `STUCK_THRESHOLD_MS`. Both rollback routes (routes/apps.ts, routes/v1.ts) do this registration around their own `relayRequest` call for exactly this reason.
- Flipping `requireHealthyEvidence` between the connection-lost recovery path and the post-success path, or defaulting it to `true` for the post-success path — the optimistic default there is what keeps a transient relay blip after a genuinely successful deploy from turning it red.
- Calling the relay directly for any new deploy trigger (a second scheduler-style call site) instead of `streamDeploy` — that was the exact scheduler bug scheduler.ts:83-92 documents, and it silently drops secret provisioning + the required-env gate, not just the health gate.
