## Relay success is a claim, not a verdict

No deploy is written to the database as `status: "success"` on the relay's word alone. `finalizeDeploy` (`backend/src/lib/stream-deploy.ts:42-94`) is the choke point every relay-reported outcome that could plausibly be a success funnels through, and it re-verifies before trusting a reported success.

`streamDeploy` (stream-deploy.ts:100-307) hands `finalizeDeploy` exactly three shapes of relay outcome that could be a success, all converging on the same function:

1. **SSE `done` event** (`handleEvent`, stream-deploy.ts:347-359) — the relay finished streaming and reported `success`/`failure` explicitly.
2. **JSON fallback** (stream-deploy.ts:193-232) — the relay doesn't support streaming and returned a single JSON body instead; `success` is derived from `data.result.success` or `data.deploy.status`.
3. **Stream ended without a `done` event** (stream-deploy.ts:270-283) — the connection closed cleanly but no terminal event arrived; success is inferred from whether every accumulated step reports `"success"` or `"skipped"`.

A fourth shape bypasses `finalizeDeploy` entirely: a **relay 4xx rejection** (stream-deploy.ts:178-187): the relay definitively rejected the deploy request (unknown app, bad branch), not a connection that dropped mid-flight. This is written straight to `status: "failed"` without going through `finalizeDeploy`, because it can never be a `relaySuccess: true` claim needing verification; there is nothing to downgrade. Routing it through the catch block's `recoverBrokenDeploy` instead would run the post-deploy health probe against whatever the PREVIOUS successful deploy left running, greenwashing a real rejection into a "success" row (the bug PR #124 fixed for rollback; the same reasoning is why both rollback routes' own RelayError-4xx branches, routes/apps.ts and routes/v1.ts, also write `failed` directly instead of calling `recoverBrokenDeploy`). 5xx and a missing body still fall through to the generic throw, which the catch block routes through `recoverBrokenDeploy` as before, since those can't be told apart from a dropped connection.

Whenever any of the three finalizeDeploy-routed shapes report `relaySuccess: true`, `finalizeDeploy` runs `verifyDeployHealth` (`backend/src/lib/post-deploy-gate.ts`, `verifyDeployHealth` near the end of the file) — container run-state via `docker compose ps` plus a public-route probe — and DOWNGRADES `success` to `false` if the verdict is unhealthy (stream-deploy.ts:53-74). A relay-reported failure routed through `finalizeDeploy` is written straight through with no second-guessing (the doc comment at stream-deploy.ts:32-40 states this explicitly). The gate exists because the relay's own internal health probe stops at the first container that answers, so a crashlooping sibling service, or a broken Traefik route invisible from inside the container network, can hide behind a `docker compose up` exit code of 0 (post-deploy-gate.ts:9-21).

## Fail-closed vs. fail-open: two calling conventions for the same gate

`verifyDeployHealth` takes a `requireHealthyEvidence` flag (doc comment on `VerifyDeployHealthOptions` in post-deploy-gate.ts) that inverts its default posture:

- **Default / optimistic (`false`)**, used by `finalizeDeploy` on the relay-success path: the absence of a bad signal is enough — an unreachable relay or an empty `docker compose ps` does not, by itself, fail the gate, because a real success signal already exists. Since 2026-08-17 this is qualified for Docker healthchecks that have not RESOLVED yet: a service with `health: "starting"` is neither offender nor clean evidence — the gate keeps polling within a bounded extension (`pendingExtraAttempts`, default 9 extra polls, so the optimistic window can grow from the base 4 × 5s ≈ 15s up to ~60s), an unreadable poll while something was "starting" carries the watch forward instead of passing, and if the window exhausts still-"starting" the deploy passes optimistically WITH a `notes` entry naming the unresolved service(s) and any offender seen earlier in the window.
- **Strict / fail-closed (`true`)**, used by connection-lost recovery below (startup recovery shares the posture via a lighter relay preflight, not this gate): there is NO success signal to trust, so only a POSITIVE confirmation (≥1 running service, none unhealthy, none still `"starting"`, and the route if set) counts; an unreachable relay, nothing running, or an unresolved healthcheck keeps the deploy `failed`. Consequence: a healthy-but-slow healthcheck (long `start_period`, Docker's default 30s interval) can consume the recovery window and be recorded failed — the reason string names the still-starting services. Margin reality check: deploy-panel's OWN images declare `HEALTHCHECK --interval=30s` with no start_period (backend/Dockerfile, frontend/Dockerfile; the prod compose overrides only db), so their health stays "starting" for ~30s after each recreate — the recovery window's last poll at ~48s clears that with ~1 poll of margin, not comfortably. agent-tasks' frontend (5s interval, 10s start_period) resolves comfortably. The same 30s-interval fact means every optimistic finalize of the panel's own stack now takes the pending extension (~30s+) instead of passing on the first poll.

**Connection-lost recovery** (`backend/src/lib/deploy-recovery.ts`, `recoverBrokenDeploy`) is invoked from `streamDeploy`'s catch block (stream-deploy.ts:284-303) whenever the relay fetch/stream throws, awaited with its own `.catch` (not fire-and-forget), so a rejection from `recoverBrokenDeploy` itself is logged and swallowed instead of becoming an unhandled rejection. It runs `verifyDeployHealth` with `requireHealthyEvidence: true` over 5 polls × 12s (deploy-recovery.ts:39-44) — containers are typically mid-recreate when a stream drops, so it deliberately waits before deciding. The same function is now also called directly (not via `streamDeploy`) from both rollback routes' non-4xx error paths, and registers/deregisters itself in `activeDeployIds` (deploy-recovery.ts:86-107) so the stuck-sweep exclusion above applies to those callers too. (Note: since the pending-health change the OPTIMISTIC gate's worst-case window, ~60s with the pending extension, is about the same length — the recovery path is stricter in posture, no longer simply "longer".)

**Startup stuck-deploy recovery** (`backend/src/lib/startup.ts`, `recoverStuckDeploys`) handles deploys still `status: "running"` more than 2 minutes after creation — the shape left behind by a self-deploy that killed the backend process mid-response, or a deploy orphaned by any other process restart. It uses a lighter relay `preflight` check rather than the full gate, but the same fail-closed posture: relay-unreachable or preflight-not-passed both resolve to `"interrupted"`, never `"success"` (startup.ts:97-113).

`recoverStuckDeploys` now runs periodically (every `CHECK_INTERVAL`, driven by `scheduler.ts`'s `startScheduler`), not only once at process boot: a deploy that was younger than the 2-minute threshold when the process booted (still legitimately in flight at that moment) would otherwise age past it later with nothing left to ever sweep it. Running periodically means each pass can now observe deploys genuinely still streaming in THIS process; it must not treat those as stuck just because they've run a while. Three things keep that safe:

1. **Exclusion set.** `activeDeployIds` (deploy-recovery.ts:6-18), consulted as the stuck-sweep query's `id: { notIn }` filter (startup.ts:69-83), holds every deploy id a process is actively driving: `streamDeploy` registers/deregisters its id for the run's duration, both rollback routes (`routes/apps.ts`, `routes/v1.ts`) do the same around their own `relayRequest` call, and `recoverBrokenDeploy` (deploy-recovery.ts:86-107) registers itself too so any caller gets the exclusion for as long as its own health-check polling runs. A running record NOT in this set is either orphaned by a past restart or was started by a process that has since died.
2. **Compare-and-set finalize.** Each candidate is finalized with `prisma.deploy.updateMany` scoped to `status: "running"` (startup.ts:137-143), not a plain `update`: if another path already resolved that exact record between the query and this write, the `count` comes back `0` and the pass leaves it (and the app status) alone instead of overwriting a newer verdict. The app-status write is additionally skipped when a still-active sibling deploy exists for the same app (startup.ts:156-166), so reclaiming an old orphaned record for an app can't clobber a genuinely live deploy's "deploying" status.
3. **Re-entrancy guard.** A module-level `sweepInFlight` flag (startup.ts:15, checked in `recoverStuckDeploys` at startup.ts:51-58) makes a second call a no-op while a pass is still running: each stuck deploy costs a `relayRequest` with up to a 300s budget, so a pass can outlast the 60s interval.

## This is the mechanism behind the self-deploy-502-but-succeeds quirk

Deploying deploy-panel's own backend kills the backend process mid-HTTP-response, so the browser/CI client sees a 502 (or a dropped connection) even though the deploy itself proceeds correctly on the relay side. The 502 is a client-side artifact of the connection dying, not a deploy failure: `streamDeploy`'s catch block fires `recoverBrokenDeploy`, which fail-closed re-verifies health once the new backend process is back up, and confirms the deploy as `success` if the app is genuinely healthy. If the backend restarts before `recoverBrokenDeploy` finishes for an in-flight deploy, `recoverStuckDeploys` catches it on its next periodic pass (every `CHECK_INTERVAL`, not only at the next process boot: see the "Startup stuck-deploy recovery" section above) and does the equivalent check via `preflight`. Either path can turn a 502-shaped client experience into a correctly-recorded `success` — this is expected behavior, not a bug: verify via `GET /api/deploys` or the DB rather than trusting the client-observed HTTP status of a self-deploy request.

## Scheduled deploys share the exact same path

`checkScheduled` (`backend/src/lib/scheduler.ts:38-103`) calls `streamDeploy` directly (scheduler.ts:93-101) rather than hitting the relay via a second, divergent call. The comment at scheduler.ts:83-92 documents why: an earlier version called the relay directly from the scheduler and skipped BOTH the pre-deploy secret provisioning and the required-env hard-fail gate, reproducing the exact `METRICS_API_TOKEN`-missing incident for scheduled deploys specifically. Routing scheduled deploys through `streamDeploy` means they get the same secret provisioning, the same three-shape relay handling, and the same trust chain described above — one implementation, not two.

## What breaks it

- Writing `deploy.status = "success"` anywhere outside `finalizeDeploy` on a relay-reported success — that bypasses `verifyDeployHealth` entirely and reopens the exact crashloop-as-healthy hole the gate exists to close.
- Adding a relay-response shape that CAN report success (e.g. a new streaming protocol) and doesn't funnel through `finalizeDeploy` — it would silently skip the health gate for that shape alone. (The 4xx-rejection shape at stream-deploy.ts:178-187 is a deliberate exception to "funnels through finalizeDeploy": it can only ever be a failure, so there is no success claim to verify.)
- Finalizing a `"running"` deploy record from the stuck-sweep with a plain `update` instead of the compare-and-set `updateMany` (startup.ts:137-143): that reopens the false-finalization race the compare-and-set exists to close, since a record another path (a rollback route, `recoverBrokenDeploy`) already resolved between the sweep's query and its write would get silently overwritten.
- Driving a deploy record's terminal status directly (not via `streamDeploy`, and not via `recoverBrokenDeploy`) without first registering its id in `activeDeployIds`: the periodic stuck-sweep has no other way to know the record is still genuinely in flight, and can finalize it out from under the caller once it crosses `STUCK_THRESHOLD_MS`. Both rollback routes (routes/apps.ts, routes/v1.ts) do this registration around their own `relayRequest` call for exactly this reason.
- Flipping `requireHealthyEvidence` between the connection-lost recovery path and the post-success path, or defaulting it to `true` for the post-success path — the optimistic default there is what keeps a transient relay blip after a genuinely successful deploy from turning it red.
- Calling the relay directly for any new deploy trigger (a second scheduler-style call site) instead of `streamDeploy` — that was the exact scheduler bug scheduler.ts:83-92 documents, and it silently drops secret provisioning + the required-env gate, not just the health gate.
