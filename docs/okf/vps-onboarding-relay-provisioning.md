## TOFU-then-pin host-key model

Onboarding a new VPS is a two-step handshake, not a single connect: `POST /api/servers/probe-vps` runs a read-only diagnostic first, then `POST /api/servers/install-relay` runs the real install. Both go through `executeSshCommand` (`backend/src/services/ssh-executor.ts:294-406`) with `acceptAnyHostKey: true` — trust-on-first-use, since a containerized backend typically has an empty `known_hosts`.

`probeVps` (`backend/src/services/probe-vps.ts:251-285`) captures the SHA-256 fingerprint of whatever host key the probe connection presents, via the `onHostKey` callback wired into `hostVerifier` (ssh-executor.ts:230-255), and returns it as `hostKeySha256` on the outcome. The install route (`routes/servers.ts`) echoes this value back as `expectedHostKeySha256` in the install request and passes it through to `executeSshCommand` (routes/servers.ts:694-696), which then PINS: `buildConnectConfig`'s `hostVerifier` (ssh-executor.ts:230-255) rejects the handshake if the presented key's fingerprint doesn't match the pinned value, flagging `_hostKeyMismatch` on the config so `classifyConnectionError` (ssh-executor.ts:127-148) surfaces it as `SshError` with `kind: "host_key_rejected"` rather than a generic `connect_failed`. A MITM or DNS hijack that swaps hosts between the probe and the install call trips this — the install aborts before `install.sh` ever runs on the wrong box.

Re-install (`POST /api/servers/:id/install-relay`) does the same pin, but sourced from the persisted `Server.hostKeySha256` rather than a fresh probe (routes/servers.ts:972-973); legacy rows created before this field existed carry `null` and fall back to TOFU, capturing the fingerprint on that re-install for next time (routes/servers.ts:985-988).

## Non-admin actors are SSRF-guarded and rate-limited; admins are not

`probe-guard.ts` exists specifically because the probe and install routes accept an arbitrary `host:port` from the request body and open a real SSH connection to it — fine for an admin, but an open internal-network prober for a broker-issued non-admin actor (probe-guard.ts:1-19 doc comment). Two independent mitigations, both skipped when `actor.isAdmin`:

- **Resolve-and-check.** `assertHostAllowedForNonAdmin` (probe-guard.ts:156-172) rejects a literal private/loopback/link-local/IPv6-ULA/IPv4-mapped address up front via `isPrivateOrLoopbackHost` (probe-guard.ts:105-140), then resolves the hostname through `dns.lookup` and re-checks EVERY returned address — catching DNS-rebinding-style attacks where the hostname itself looks public but resolves to internal space. A DNS-lookup failure passes through as allowed at this pre-check, a deliberate fail-open distinct from the stricter fail-closed posture `post-deploy-gate.ts`'s route probe uses for the same private-host check; the connect-time check below refuses a failed lookup for guarded servers.
- **Sliding-window rate limit.** `consumeProbeQuota` (probe-guard.ts:279-290) caps a non-admin actor at 5 probe calls per 60-second window, keyed by `actor.userId`, in-memory only (single-instance; a multi-replica deploy is a known follow-up per the module doc comment).

Both `POST /api/servers/probe-vps` and `POST /api/servers/install-relay` apply the SAME `assertHostAllowedForNonAdmin` check (routes/servers.ts:480-481, :596-597) — the install route re-checks rather than trusting the probe's earlier check, so a non-admin can't bypass the guard by skipping straight to install.

The restriction also covers registered servers and the later use of their stored targets, in these places only. For a non-admin, `POST` and `PATCH /api/servers` reject a `host` or `relayUrl` host the guard denies (400 `private_host`, the body names the `field`). `assertServerTargetsAllowed` (probe-guard.ts:221-251) re-checks the stored targets right before the panel connects: `host` before SSH in `:id/install-relay` and `:id/update-relay-image`, and `relayUrl` in `:id/test`, `:id/system`, `:id/relay-status`, `:id/relay-self-update` and `:id/update-relay-image`, in `POST /api/servers/:serverId/sync`, in the `appsRouter` middleware (every route under `/api/servers/:serverId/apps`) and in the `/api/v1` routes `deploy`, `rollback`, `logs` and `preflight` (all through `denyPrivateServerTargets`, lib/target-guard.ts). A stored `relayUrl` that is not a URL answers 400 `invalid_relay_url`. A server whose id is listed in `TRUSTED_RELAY_SERVER_IDS` (`backend/src/config/index.ts`, operator-set backend environment) is exempt at these use sites only (`assertServerTargetsAllowed` takes the stored row's id as an optional third argument), and for a non-admin its `host` and `relayUrl` are pinned: `PATCH /api/servers/:id` that changes either answers 403 `trusted_server_locked` and `:id/install-relay` keeps the stored `relayUrl`. `POST /api/servers` and the installer-printed relay URL never pass an id and stay checked. The name inside the pinned `relayUrl` is not re-resolved at use. The relay URL the installer prints is checked before a first install or re-install stores it (SSE `error` with `kind` `private_host`, or `relay_url_invalid` for a placeholder). The literal classification in `isPrivateOrLoopbackHost` (probe-guard.ts:105-140) uses `net.BlockList` ranges plus the embedded IPv4 of `::/96`, `::ffff:0:0/96` and `64:ff9b::/96`, so full-form IPv6 spellings are covered. Every relay request goes through `relayFetch` (lib/relay-fetch.ts) or sets `redirect: "manual"` (the streamed deploy; the guarded transport never follows a redirect either), so a relay's `3xx` is a relay error and never followed, for admins too. The scheduler (lib/scheduler.ts) runs the same relayUrl check for servers with a `userId` before it calls the relay and records a denied scheduled deploy as a failed deploy. The check resolves the name itself and the connection resolves it again, so the connection re-checks (`backend/src/lib/connect-guard.ts`): for a server row with an owner (`userId` set) that is not listed in `TRUSTED_RELAY_SERVER_IDS`, relay HTTP goes through `guardedFetch` (`lib/guarded-fetch.ts`, `node:http(s)` with `guardedLookup`, selected by `relayFetch`'s `guarded` option and `streamDeploy`'s `connectGuard`) and SSH resolves once with `resolveCheckedAddresses` and connects ssh2 to the checked IP (`guardTarget` on `executeSshCommand`). The same classifier applies, a lookup error is a refusal, and an IP-literal host is classified directly because Node skips `lookup` for it. An admin actor is not guarded on the request paths that pass it (servers, apps, sync and `/api/v1` routes); `relayRequest` calls made without an actor (secret provisioning, deploy recovery, the post-deploy gate, the startup sweep, scheduled deploys) follow the row owner. Not covered: the pre-check itself still lets a failed DNS lookup pass, and the name inside a listed row's `relayUrl` is never re-resolved.

## Persisted install metadata: re-install and update-image must not clobber hand-customization

`Server` persists four install-time facts (`backend/prisma/schema.prisma:14-47`): `hostKeySha256` (above), `relayMode` (the resolved `greenfield` / `existing-traefik` / `port-only` mode `install.sh` reports), `relayDir` (the VPS path holding the relay's compose file, defaulting to `/opt/agent-relay` when unset), and `relayComposeFile` (the compose filename, for operators who installed a customized prod override with `container_name: agent-relay` + Traefik labels rather than the installer default). Re-install and update-image read these back as defaults (`routes/servers.ts:905-923`) rather than assuming the installer default every time — an operator who manually customized `relayDir` or the compose filename would otherwise have that customization silently overwritten by a re-install or image-update call using the wrong path/file.

## Per-server / per-actor concurrency locks

`active-installs.ts`'s `activeInstalls` Set (a single in-memory registry, same single-instance caveat as the rate limiter) is keyed by operation-and-target strings: `reinstall:<serverId>`, `update-image:<serverId>`, `self-update:<serverId>`, plus per-actor keys. `isServerMutating` (active-installs.ts:24-30) checks only the per-server keys — re-install, update-image and relay self-update all mutate the same relay container, so an in-flight one blocks the others on the SAME server (routes/servers.ts:860-878, the "Two locks" comment), while re-installs of two DIFFERENT servers proceed in parallel. The per-actor keys additionally limit one actor to one in-flight first-install (bare actor key, routes/servers.ts:635-642) and, separately, one in-flight re-install (`reinstall-actor:<actor>` key, routes/servers.ts:871,854-861) regardless of target server — install and re-install do not share a lock.

## What breaks it

- Any new route that opens an SSH connection to a caller-supplied host without going through `executeSshCommand`'s host-key handling AND, for non-admin callers, `assertHostAllowedForNonAdmin` — both the pin and the SSRF guard live in that path only.
- Skipping the install route's own `assertHostAllowedForNonAdmin` call on the assumption the probe already checked it — the two calls are for two different requests and neither trusts the other.
- Re-install or update-image defaulting `relayDir`/`relayComposeFile` to the installer default instead of the persisted `Server` value — that is exactly the hand-customized-setup clobber this metadata exists to prevent.
- Adding a new mutating install-family route without registering it in `active-installs.ts` under a per-server key — it would run concurrently with re-install/update-image against the same relay container with no lock.
