# API reference

All endpoints are served by the Hono backend on `PORT` (default `3001`) and prefixed with `/api`. The UI uses the bare `/api/...` paths with cookie-session auth; CI/CD pipelines should use `/api/v1/...` with a `dp_` API key (recommended) or the `PANEL_TOKEN` as a Bearer token.

## Health

| Method | Path          | Description              |
|--------|---------------|--------------------------|
| GET    | `/api/health` | Health check, returns OK |

`/api/health` only proves the Hono process is up. For end-to-end verification (auth + Prisma queries + fleet reachability), run `scripts/smoke-check.sh`.

## Servers

| Method | Path                              | Description                                          |
|--------|-----------------------------------|------------------------------------------------------|
| GET    | `/api/servers`                    | List all servers (includes app count)                |
| GET    | `/api/servers/:id`                | Get a single server with its apps and deploy count   |
| POST   | `/api/servers`                    | Add a new server. A non-admin caller gets `400` `private_host` (with `field`: `host` or `relayUrl`) when the `host` or the `relayUrl` host is private, loopback, link-local or resolves to such an address; see [Private targets](#private-targets-for-non-admin-callers) |
| PATCH  | `/api/servers/:id`                | Update server fields. The same `400` `private_host` applies to a non-admin caller for the `host` and `relayUrl` in the body |
| DELETE | `/api/servers/:id`                | Delete server (cascades to apps and deploys)         |
| POST   | `/api/servers/:id/test`           | Test relay connectivity, pings relay `/health` and returns `relay` (`{ status, version, revision }`), `relayRevision`, `latestRevision` (from GHCR `latest`) and `relayOutdated` (`true`, `false` or `null` when unknown). The answer's `status` (persisted to `Server.status`) distinguishes the failure kinds: `online` (relay answered 2xx), `auth` (relay answered 401/403: the stored relay token is wrong or missing; the `message` says to check the relay token), `unknown` (any other non-2xx answer, a 2xx answer whose body is not JSON, or the 5 s probe timed out) and `offline` (connection refused, DNS failure or another network error; only network failures are `offline`). A local exception (database error) is not a relay status: it answers `500` and leaves `Server.status` unchanged |
| GET    | `/api/servers/:id/relay-status`   | Check relay revision against the GHCR `ghcr.io/lannguyensi/agent-relay:latest` revision without mutating database server status; returns `{ relayRevision, latestRevision, relayOutdated, state }` (`state` is `current`, `outdated` or `unknown`) |
| POST   | `/api/servers/:id/relay-self-update` | Trigger credential-free relay self-update (`POST /api/self-update` on the VPS relay, optional `{ tag }`), then poll `/health` (about 30 s) until the relay restarts on the target revision; returns `200` (`{ status: "online", previousRevision, relayRevision, latestRevision, relayOutdated }`), `400` when the server has no `relayUrl` or invalid body, `429` (`rate_limited`) if a server mutation is already in progress, `409` if the relay is busy with a deploy/rollback/self-update, `422` when the relay refuses self-update (e.g. build-based compose install, compose-pinned image differs from the target) or does not support it yet (`kind: "self_update_unsupported"`, relay answered `404`/`405`; update once over SSH), `504` (`trigger_timeout`) when the relay does not answer the trigger within 60 s, or `502` on unreachable relay (`trigger_unreachable`, sets the server `offline` for a network failure), a relay that already failed its pre-trigger `/health` probe and returns a non-2xx trigger answer (`relay_down`; the server status follows the shared probe classifier: `offline` for a network failure, `auth` for 401/403, `unknown` for other answers such as Traefik's 404/502 for a stopped container), another relay error, or poll timeout; the unsupported, timeout and other-error answers leave the server status unchanged. When the poll window ends without a verified new revision, the panel reads the relay's own record (`GET /api/self-update`, best effort; ignored when the relay has none, answers 404/405, the read fails, or the record cannot be shown to belong to this attempt: it must be requested after the trigger (120 s clock-skew allowance), agree with the known previous and target revisions, and match at least one of them). On a trigger timeout the relay has not yet written its new record (it pulls the image first), so only an `in_progress` record whose previous revision matches the pre-trigger `/health` revision counts, answering `202` pending; anything else keeps `504`. On the poll-window path: `succeeded` answers `200` like a verified update with `source: "relay_record"` (only when the resulting revision equals the known target, or, with no known target, differs from the previous revision; otherwise the record gives no verdict), `failed`/`refused` answer `502` (`relay_reported_failed`, with `relayStatus`, `relayError` and the helper's exit code and logs in `message`), and `in_progress`/`unverified` answer `202` `{ status: "pending", kind: "relay_in_progress"|"relay_unverified", relayStatus, message }`, which is not a failure. A verified `/health` revision always wins and the record is not read |
| GET    | `/api/servers/:id/system`         | Get system info (CPU, memory, disk) from relay       |
| POST   | `/api/servers/:serverId/sync`     | Sync apps list from relay to local database. On a failed request to the relay it answers `500` with `{ error, status }`, where `status` (also persisted to `Server.status`) is `auth` for a relay `401`/`403` (the stored relay token is wrong or missing), `unknown` for any other relay error answer, an answer that cannot be parsed (not JSON, or an apps list of the wrong shape) or a timeout, and `offline` only for a refused connection, DNS failure or another network error. A relay URL removed meanwhile answers `400` (`no_relay`, status `no-relay`: a configuration state, not reachability), a vanished server row `404`, and a local exception (database error) a `500` with no `status` and `Server.status` unchanged. A per-app detail call that fails marks that app `offline` only when the relay was unreachable, otherwise `unknown` |
| POST   | `/api/servers/install-relay`      | Onboard a new VPS: installs agent-relay over SSH and creates the server row on success. Streams progress as SSE (`progress`, `error`, `done` events); one install at a time per actor (429 otherwise), 409 if the host is already registered |
| POST   | `/api/servers/:id/install-relay`  | Install or reinstall agent-relay on the VPS over SSH (long-running; locks per server and per actor). Streams progress as SSE |

### Private targets for non-admin callers

A caller that is not an admin cannot make the panel connect to a private, loopback, link-local (including the cloud metadata address) or reserved address, or to a name that resolves to one. Besides `POST` and `PATCH /api/servers`, `probe-vps` and the first `install-relay`, the check runs on the server's stored targets before the panel connects: `host` for the per-id `install-relay` and `update-relay-image`, and `relayUrl` for `:id/test`, `:id/system`, `:id/relay-status`, `:id/relay-self-update`, `update-relay-image`, `POST /api/servers/:serverId/sync`, every route under `/api/servers/:serverId/apps/...`, and `POST /api/v1/deploy`, `/rollback`, `/preflight` and `GET /api/v1/logs`. A denied target answers `400` `{ error: "private_host", field: "host" | "relayUrl", message }`; a stored `relayUrl` that is not a URL at all answers `400` `invalid_relay_url`. The relay URL that the installer prints is checked the same way before a first install or re-install stores it (the SSE `error` event carries `kind: "private_host"`, or `relay_url_invalid` when the installer printed a placeholder instead of a URL; re-run the install with a public relay domain). Admins are never filtered. The panel does not follow redirects from a relay, for any caller including admins: a `3xx` answer is a relay error (`502`), so a `relayUrl` that redirects must be set to its final URL. A server whose id is listed in `TRUSTED_RELAY_SERVER_IDS` (backend environment, see `docs/configuration.md`) is exempt from the check on its stored targets, and for a non-admin its `host` and `relayUrl` are pinned: `PATCH /api/servers/:id` that changes either answers `403` `trusted_server_locked`, and a re-install keeps the stored `relayUrl`. `POST /api/servers` and the installer-printed relay URL are still checked. A scheduled deploy for a server owned by a non-admin runs the same `relayUrl` check before it calls the relay; a denied one is recorded as a failed deploy whose step message names `private_host`. Connect-time check: besides that pre-check, the panel resolves the name again inside the connection and refuses a private, loopback, link-local or reserved address (the same classifier; a lookup error, an empty answer or an unusable address family is a refusal too), so a DNS record that flips between the pre-check and the connection, or a lookup that failed at check time, does not reach an internal address. Relay HTTP requests of such a server (`relayRequest`, the relay calls in the server routes, `streamDeploy`) go through a lookup that does this check; SSH connects over a socket whose lookup runs the same check, so the name is resolved once and every address Node may try is classified. A refused connection fails like an unreachable relay or host: a relay call rejects with `TypeError: fetch failed` whose `cause` carries the code `ECONNDENIED` (so the relay probes report the server `offline`), SSH rejects with `connect_failed`. The guarded relay transport gives up on a connection that does not complete within 10 seconds (cause code `ETIMEDOUT`, also `offline`), like the global fetch. It applies to a server with an owner (`userId` set) whose id is not listed in `TRUSTED_RELAY_SERVER_IDS`, decided by the stored row, so the scheduler, the startup sweep and the post-deploy health checks are covered without a request actor. An admin actor is never filtered: the request paths that have an actor pass it. The helpers that run without one (pre-deploy secret provisioning and the required-env check, deploy-outcome recovery, the post-deploy gate, the startup sweep) follow the row, so an admin who deploys a non-admin-owned server is held to the same check on those calls. A server without an owner (the admin-shared fleet) and a server listed in `TRUSTED_RELAY_SERVER_IDS` are exempt at connect time as well. The pre-check itself still lets a failed DNS lookup pass; the connect-time lookup is what refuses it.

## Apps

All app endpoints are nested under a server: `/api/servers/:serverId/apps`.

| Method | Path                                            | Description                                    |
|--------|-------------------------------------------------|------------------------------------------------|
| GET    | `/api/servers/:serverId/apps`                   | List apps for a server (database only, no relay call); each app carries `lastDeployOutcome` (the Deploy outcome of its newest deploy, `null` when there is no verdict). Apps tagged `ignored` (hidden via `DELETE /api/servers/:serverId/apps/:name`) are excluded unless `?showIgnored=true`                          |
| GET    | `/api/servers/:serverId/apps/upstream`          | Staleness per app: `{ upstream: { <appName>: { branch, deployedCommit, remoteHead, checkedAt, state, reason? } } }`. `state` is `current`, `behind` or `unknown` (`reason` when unknown). Taken from the relay's `GET /api/apps` (one call per request, 8s budget) and validated by the panel; same ownership check as the list. Anything doubtful yields `unknown`, never `current`, with a `reason`: `relay unreachable`; `relay listing unavailable` (answer without an `apps` array); `relay does not list this app` (absent from the listing); `app not configured on relay` (listed as `configured: false`); `relay does not report upstream` (configured entry without the field, e.g. an older relay); or a malformed value or a verdict that contradicts its commits. `behind` means the deployed commit differs from the remote branch head. The UI shows the GitHub compare link only when `App.repoUrl` is set (nothing in the panel sets it today) |
| POST   | `/api/servers/:serverId/apps/:name/deploy`      | Trigger deploy (proxied to agent-relay). Provisions panel-managed secrets into the deploy dir's `.env` first and hard-fails before reaching the relay if a declared-required env key still resolves empty — see docs/configuration.md#app-secrets |
| POST   | `/api/servers/:serverId/apps/:name/rollback`    | Trigger rollback (proxied to agent-relay). A `to_commit` in the body must be a full or abbreviated commit sha (7 to 40 hex characters; the empty string counts as malformed, an absent one means the previous version), else 400 `bad_request` before anything is stored or the relay is called; a well-formed but unreachable sha ends as a `failed` row with the relay's `before_reset` message, same as the `POST /api/v1/rollback` row. **Does not** provision secrets or run the required-env gate — see the "Rollback is exempt" note in docs/configuration.md#app-secrets. | GET    | `/api/servers/:serverId/apps/:name/secrets`     | List panel-managed secret keys for the app (masked — key name + set/unset only, never the value) |
| PUT    | `/api/servers/:serverId/apps/:name/secrets/:key`| Set (create or update) one secret; body `{ value }`. Write-only — the value is never echoed back |
| DELETE | `/api/servers/:serverId/apps/:name/secrets/:key`| Delete one secret |
| PUT    | `/api/servers/:serverId/apps/:name/required-env-keys` | Declare which env keys the app requires; body `{ keys: string[] }` (replace-all). Drives the preflight/deploy hard-fail gate — see docs/configuration.md#app-secrets |
| PATCH  | `/api/servers/:serverId/apps/:name/tag`         | Set the app tag; body `{ tag }` where tag is `production`, `development`, `ignored` or `null` (clears) |
| PATCH  | `/api/servers/:serverId/apps/:name/live-url`    | Set or clear the app's live URL; body `{ liveUrl }` (http/https URL, empty string or null clears) |

| GET    | `/api/servers/:serverId/apps/:name/deploys/:deployId` | Get one deploy by id, scoped to this server (404 if it belongs to another server); the `:name` segment is not checked. Carries `outcome` (see [Deploy outcome](#deploy-outcome)) |
| POST   | `/api/servers/:serverId/apps/bulk-deploy`       | Deploy several apps in one call; body `{ apps: string[], force?: boolean }` (deduplicated, at most 50 per call; `force` defaults to `false`, so a preflight failure blocks the app). ## API v1 (CI/CD pipeline integration)

All v1 endpoints are prefixed with `/api/v1` and authenticated with a Bearer credential: either a `dp_` API key (what the bundled GitHub Action uses) or the `PANEL_TOKEN`. They return JSON and are designed for non-interactive callers (GitHub Actions, GitLab pipelines, cron jobs).

| Method | Path                  | Description                                                        |
|--------|-----------------------|--------------------------------------------------------------------|
| GET    | `/api/v1/servers`     | List all servers                                                   |
| GET    | `/api/v1/apps`        | List all apps (optionally filtered by `server_id`, which accepts a server name or id). `server_id` set to a server you don't own, or that doesn't resolve, answers 404 rather than an empty list. Apps tagged `ignored` are always excluded; there is no `showIgnored` equivalent here |
| POST   | `/api/v1/deploy`      | Trigger a deploy for a given app                                   |
| GET    | `/api/v1/deploy/:id`  | Get status of a specific deploy. `steps` is always an array: a deploy blocked by preflight has one failed step per failed check (`name`, `kind: "preflight-check"`, `status: "failure"`, `message`, `output`, `critical`); older rows that stored a raw preflight report or a string are converted on read. Carries `outcome` (see [Deploy outcome](#deploy-outcome)). |
| GET    | `/api/v1/deploys`     | List deploys with `limit` (default 50, max 200) and `offset` / `total` pagination, optionally filtered by `server_id` (accepts a server name or id), `app_id`, `app` (an app NAME) and `status`. `server_id` set to a server you don't own, or that doesn't resolve, answers 404 rather than an empty list. `app_id` is an app id only (app names are unique per server, not globally). The `app` filter matches the app name (validated against the v1 app-name pattern, an invalid one answers 400): with `server_id` it is that server's app of that name, without it the match spans every server the caller can see, so the same name on several servers matches all of them (documented, not an error). `app` and `app_id` together answer 400 `bad_request` (two unrelated app filters would silently AND into an always-empty result). Unknown query parameters are ignored, not errors. Carries `outcome` (see [Deploy outcome](#deploy-outcome)). |
| POST   | `/api/v1/rollback`    | Trigger a rollback for a given app. `to_commit` (optional) names the target commit: a full or abbreviated commit sha, `^[0-9a-fA-F]{7,40}$`; a present-but-malformed one (7-40 hex required, so `HEAD~1` and the empty string too) answers 400 `bad_request` before anything is stored or the relay is called, absent means the previous version. A well-formed sha the repository cannot roll back to is not caught here: the relay refuses it with a `before_reset` 4xx and the row ends `failed` with that message. Answers `202` with `deploy.status: "running"` and finishes asynchronously: poll `GET /api/v1/deploy/:id` until `status` leaves `running` (`rolled_back` or `failed` from the relay's answer, or `success`, `failed` or `interrupted` when connection-lost recovery finalized the row; a rollback the panel cannot prove ran ends `interrupted`). App status: blocked by preflight or a relay-reported `success: false` sets `unhealthy`; a relay-reported success sets `healthy` only after the post-deploy health gate passes, `unhealthy` otherwise (the app status can lag the polled row by the length of the gate). A relay 4xx marks the row `failed`; the relay tags its rollback error with a `phase`, and an `after_reset` 4xx (the relay attempted `git reset --hard`, e.g. `Rebuild failed` or a reset that failed part-way) sets the app `unhealthy`, while a `before_reset` 4xx (bad ref, unknown app; HEAD did not move) or an untagged one from an older relay leaves the app status untouched |
| GET    | `/api/v1/logs`        | Fetch logs for a given app                                         |
| POST   | `/api/v1/preflight`   | Run preflight checks for a given app                               |

### Request parameters

`server` is a server name or id in every route below.

- `POST /api/v1/deploy`: body `{ server, app, force?, ref? }`. `app` must already be known to the panel (see `POST /api/servers/:serverId/sync` above), otherwise 404; this route does not create apps. `ref` is passed to the relay as the branch. Answers 422 when the server has no relay, and 202 with `{ deploy: { id, status, server, app, triggeredBy } }` on success.
- `POST /api/v1/rollback`: body `{ server, app, to_commit? }`. As with deploy, an app the panel does not know answers 404. `to_commit` must be a full or abbreviated commit sha (7 to 40 hex characters); a present-but-malformed value, the empty string included, answers 400 `bad_request` before the deploy row is created, and an absent one means the previous version. Reachability of a well-formed sha stays the relay's verdict: an unreachable one ends as a `failed` rollback row carrying the relay's `before_reset` message.
- `GET /api/v1/logs`: query `server`, `app`, `lines` (1 to 1000, default 50).
- `POST /api/v1/preflight`: body `{ server, app }`. Returns the relay's `{ passed, checks }`, including the panel's required-env check when the app declares required keys.

Example: trigger a deploy from a CI job.

```bash
curl -X POST https://panel.example.com/api/v1/deploy \
  -H "Authorization: Bearer $PANEL_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"server": "prod-1", "app": "web-prod"}'
```

The response includes a deploy id you can poll via `GET /api/v1/deploy/:id` to wait for `success` / `failed` / `interrupted` (the relay connection was lost and the panel could not prove the deploy reached its target). Deploying the panel's own app restarts the panel mid-request, so the poll fails until the panel is back; read the same id again then. The Deploy Panel GitHub Action polls this endpoint with that same tolerance, retrying transient failures (a refused connection, a proxy `5xx`, `404`, `408` or `429`, an unparsable body) with backoff until its `timeout` and failing on a settled status, a `401`/`403`, another unexpected HTTP code, or its timeout, so a self-deploy that restarts the panel is waited out rather than reported as a failure. A record settled by the sweep or by connection-lost recovery after a relay proof carries `commitBefore`, `commitAfter` and `duration` taken from the relay's history entry for the deploy (the `commitBefore` / `duration` stay `null` when the entry has none); one it could not prove carries none. The sweep also runs the post-deploy health gate before it records `success`: a deploy whose relay proof holds but whose services are not all up, or whose `liveUrl` answers as down, ends `failed` (app `unhealthy`) with the offending services in a `post-deploy health gate` step, and while a service is still restarting or starting, or the route is briefly down, within ten minutes of the start (of the panel process's start too, for the panel's own app) the row stays `running` and a later pass looks again. A gate that gives no verdict within two minutes is not a result: inside those ten minutes the row waits, after them it ends `interrupted` (app `unknown`, no commits) although the relay proof holds. Apps left on `deploying` with no running deploy for more than two minutes are settled from their latest finished deploy (`success` is `healthy`, `failed` is `unhealthy` unless the relay rolled back and the rollback health check passed, anything else `unknown`).

## Other endpoints

The backend also exposes endpoints that the panel UI itself uses. They are not part of the stable CI/CD (`/api/v1`) surface and may change:

- `/api/auth/*`: admin token login and logout (`POST /login`, `POST /logout`), GitHub OAuth (`/github/config`, `/github/start`, `/github/callback`), the identity-broker registration endpoint (`POST /api/auth/register-from-project-pilot`), and `/api/auth/check`. See [configuration.md#authentication](configuration.md#authentication).
- `/api/api-keys`: create, list, and revoke `dp_` API keys (panel-session auth only; rejects API-key auth).
- `/api/servers/probe-vps` and `/api/servers/:id/update-relay-image`: VPS provisioning helpers used by the server-management UI. `update-relay-image` also streams progress as SSE.

### Deploy outcome

A deploy row ends `failed` for two very different situations, so the deploy responses (`GET /api/servers/:serverId/apps/:name/deploys/:deployId`, `GET /api/deploys`, `GET /api/deploys/:id`, `GET /api/v1/deploy/:id`, `GET /api/v1/deploys`) carry a derived `outcome`, computed from the stored steps (`classifyDeployOutcome` in `backend/src/lib/deploy-log.ts`):

| `outcome` | When |
|-----------|------|
| `success` | status `success` |
| `rolled_back_healthy` | status `failed` and the last `rollback: health check` step (streamed by agent-relay after an automatic rollback) has status `success`: the app runs the previous version, a warning and not an outage |
| `outage` | status `failed`, the log is a relay step stream (a steps array with at least one step), and that step failed or was skipped (`ROLLBACK UNHEALTHY`), or it is absent: rollback disabled, blocked or failed before the health check, or a relay that predates the step. Healthy is never assumed without the step, so an older relay keeps today's behaviour: every failed forward deploy with a step stream is an `outage` (red "Failed") |
| `null` | no verdict: `running`, `pending`, `interrupted`, `rolled_back` (a manual rollback row), a `failed` row whose log is not a relay step stream (a failed manual rollback stores the raw relay result object, a nested `{ result }` preflight block, `[{ error }]` or a bare string; the app may well still be running), a missing or unparsable log, a failed deploy with no steps (the stream ended before the first step), a deploy blocked at preflight and a relay 409 conflict |

The status stays `failed`. `App.status` becomes `healthy` for `rolled_back_healthy` (the previous version serves; `lastDeployAt` is not advanced) and `unhealthy` for every other failed deploy; `outcome` also tells the UI and the MCP tools whether the app is down. The panel shows `rolled_back_healthy` as an amber "Failed, rolled back (healthy)" badge with a note, an `outage` as the red "Failed" badge (with a danger note when the rollback health check itself failed).
